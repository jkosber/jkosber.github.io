IPv6 packet investigations

A CSIA 210 final capstone that matched Windows hosts' IPv6 behavior to DHCPv6 replies and router advertisements, including a lost gateway traced to one advertisement.

Role

Filtered the course's capstone traces, found the frames behind each host's behavior, compared them with the host output and wrote up the conclusions. Building or repairing the network was not part of the work.

  • Wireshark
  • DHCPv6 and ICMPv6 display filters
  • Windows ipconfig output from the course

A Windows host can have an IPv6 address and still fail to reach another network. The CSIA 210 final capstone was about finding out why from the packets: which reply assigned an address, which hosts shared a duplicate, which source address a host picked, and what made a gateway disappear.

The course provided the traces, the network diagrams and the hosts' ipconfig output. From those, I filtered the traffic, found the frames that explained each symptom, compared them with the host output and wrote up the conclusions.

Environment and analysis method

The traces came from a network with Windows hosts, DHCPv6 and a layer 3 device sending router advertisements, with IPv4 running alongside. Every IPv6 address here uses the 2001:db8::/32 documentation prefix. These four filters did most of the work:

Filter What it shows
dhcpv6.msgtype == 7 DHCPv6 Reply messages, to find the one that assigned an address
dhcpv6.iaaddr.ip == 2001:db8:1ab:1001::108 Replies carrying the address the Windows host reported
icmpv6.type == 134 Router advertisements, with their flags, prefixes and router lifetime
ipv6 The wider IPv6 sequence, including address changes and neighbor discovery

Finding the DHCPv6 address assignment

In the first trace, the question was which reply gave the Windows 10 host its address. I filtered for DHCPv6 replies and checked their IA Address options. Frame 9306 was the first reply carrying the host's address, ending in ::108. Earlier replies carried ::109, so the message type alone wasn't enough; the IA Address field is what tied the reply to the host.

Frame 9306 field Value
Message type Reply (7)
UDP ports 547 to 546, server to client
Option IA Address (5)
Address 2001:db8:1ab:1001::108
Preferred and valid lifetime 120 and 180 seconds

Separating a duplicate address from general connectivity

In the second trace a Windows 7 host had been set by hand to ::117, the address the Windows 10 host already held. I compared their source MAC addresses in the neighbor discovery traffic with the Windows 7 host's ipconfig output, which marked the address as a duplicate.

A normal ping still worked, over IPv4, with two replies. Forcing IPv6 failed. That forced attempt also showed a name-resolution error, so the duplicate flag and the neighbor discovery comparison are what point to the conflict, not the failed ping alone. My summary put it this way: "With dual stack setup it fell back to IPv4 which worked but when you tried to force IPv6 pings it failed outright."

Tracking source-address changes

Later in the same trace I followed the Windows 10 host as it picked up public and temporary SLAAC addresses next to its DHCPv6 address, ::117:

Point in the trace Finding
Router advertisement Managed flag set; on-link and autonomous prefix flags set
Frame 6913 The host used its temporary SLAAC address as the source
Frame 7512 A later advertisement with the autonomous flag off
Host output after that Both SLAAC addresses deprecated; a later packet used the DHCPv6 address ending in ::117

My submission said the autonomous flag turning off deprecated the SLAAC addresses. That overstates it: an unset autonomous flag makes the host ignore that prefix information, and an address is deprecated when its preferred lifetime runs out (RFC 4862, section 5.5.3). Pinning down the timing would take the full lifetime sequence from the trace.

Losing the gateway while retaining the address

Later in that trace the Windows 10 host kept a preferred IPv6 address but lost its IPv6 gateway, and traffic to an off-link destination failed. I filtered the router advertisements and lined up their router lifetimes with what the host did:

Point in the trace What happened
Frame 1 A router advertisement with a 270-second router lifetime
Frame 9660 The first of an earlier group of four pings
Frame 9725 A router advertisement with lifetime 0; the host dropped its IPv6 default gateway
Host output The IPv6 address stayed preferred; only the IPv4 gateway was listed
Frame 9887 A new advertisement brought the 270-second lifetime back
Frame 9991 The first ping of the later group, with connectivity restored

A router lifetime of 0 removes that router as a default gateway, and a later advertisement with a nonzero lifetime adds it back (RFC 4861, section 6.3.4). The DHCPv6 lease never supplied the gateway, which is why the address survived. My conclusion in the capstone: "This lab showed that IPv6 address state and IPv6 default gateway state are independent and a single RA can break IPv6 connectivity."

What remained visible in encrypted traffic

The same capstone looked at SSH (frames 27218 and 27364) and HTTPS (frames 27902 and 29910). Only the banners and algorithm names were readable; the application data wasn't. I didn't decrypt either session.

Limits

  • The traces aren't in the repository, so the frame numbers can't be rechecked from it. The screenshots show frame 9306, the router advertisement flags, the SSH frames and the first advertisement in the second trace; the other frame numbers come from the written answers.
  • The submission doesn't include the host output I compared the ::108 match against.
  • I diagnosed the duplicate address but didn't fix it or retest.
  • The SLAAC explanation above corrects what the submission said.
