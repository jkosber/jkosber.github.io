Networking I was the first course in Cisco's CCNA sequence: how devices address and find each other, how to set up switches and routers, and how to troubleshoot when a client can't reach something. I did the labs in Packet Tracer and turned in a write-up for each one.

What the course provided and what I did

The course provided the Cisco Networking Academy activities and lab sheets: the topologies, addressing tables, steps and sample output, and the starting device configurations. My part:

  • Filled in the addressing tables and subnet plans, including two VLSM designs
  • Wrote what was wrong on each device in the troubleshooting labs and the change that fixed it
  • Answered the lab questions on IOS, switching, ARP, IPv6 and TCP and UDP from what Packet Tracer's simulation mode showed
  • Ran live Wireshark captures for the Ethernet and ICMP labs

The device configurations are inside the Packet Tracer files, which GitHub can't display. This page draws on the written answers.

Strongest work

Designing a VLSM plan (11.10.1)

The lab provided two routers, four LANs that needed 32, 21, 19 and 8 host addresses, and a link between the routers. The plan had to be contiguous, largest subnet first, with the smallest possible subnet on the router link.

The plan gave the largest LAN a /26, the next two a /27 each, the smallest a /28 and the router link a /30. A /27 only has 30 usable addresses, so it couldn't fit 32 hosts. The table shows the plan on the documentation range 192.0.2.0/24, with the same sizes and order as the submission:

Segment Hosts needed Subnet Usable range Broadcast
Largest LAN 32 192.0.2.0/26 .1–.62 .63
Second LAN 21 192.0.2.64/27 .65–.94 .95
Third LAN 19 192.0.2.96/27 .97–.126 .127
Smallest LAN 8 192.0.2.128/28 .129–.142 .143
Router link 2 192.0.2.144/30 .145–.146 .147

Scroll horizontally to read the full table on a narrow screen.

In each LAN the router took the first usable address, the switch the second and the client the last, so the plan doubled as the device addressing table.

One mistake in the submission: the largest LAN's client got the address ending in .63. That's the /26's broadcast address, which the submission's own subnet table lists correctly. The client should have been .62.

Troubleshooting a web server outage (17.7.6)

Four clients couldn't reach a web server after a second DNS server was added. The lab allowed changes to the clients and the local router, but not the ISP cloud or the servers. I checked each client's settings in Packet Tracer's command prompt against the addressing table, then used ping and the browser:

  • PC-01 had the wrong IP address. After I corrected its address, it reached the gateway, the web server and PC-02.
  • PC-02 had the wrong default gateway. Fixing it brought back web access.
  • PC-A could ping its neighbor but not its gateway or anything beyond it, which pointed at the router. R1's G0/1 address was wrong, and correcting it let the two LANs reach each other.
  • PC-B could reach the server by IP but not by name. I corrected its DNS setting, and the write-up notes that DNS2 itself still had a problem the server's owner would need to fix.

From the lab write-up: "PC-A can only access the local lan and not other networks so I corrected the G0/1 interface ip address."

Fixing default gateway faults (10.3.5)

Two LANs sat behind one router with four faults planted in them. After I filled in the missing gateways in the addressing table, ping tests between devices located each fault:

  • PC1 couldn't reach PC2 because its address didn't match the network it was wired to. Fix: the right address.
  • Nothing could ping S2 because S2 had no IP address. Fix: an address, set with ip address.
  • PC4 couldn't be reached because its default gateway was wrong. Fix: the correct gateway.
  • Remote hosts couldn't ping S1 because it had no default gateway. Fix: a gateway, set with ip default-gateway.

I left the lab sheet's own test table at the end mostly blank, so there's no written retest.

Following IPv6 Neighbor Discovery (9.3.4)

Simulation mode showed a PC finding another PC's MAC address with Neighbor Discovery instead of ARP. The write-up lists the ICMPv6 message types (128 and 129), the solicited-node multicast destination and its matching Ethernet address, and explains why a second ping needed no discovery at all. For a host on another network, the PC used the router's MAC instead. The write-up explains the multicast choice: "A multicast address is used so only selected addresses would be listening to an ND message unlike a broadcast."
